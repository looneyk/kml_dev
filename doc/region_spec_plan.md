# Region Specs --- Plan

Date: 2026-11-03

`RegionSpec` contains the elements that go into the creation of a region, its subregions, and its zones. RegionSpecs are the drivers of worldspace and zone creation.
A spec has the
region's properties, its worldspace's coordinate system for top-level specs, its extent, patterns for or references to the `RegionSpec`s
of its subregions and the `ZoneSpec`s of its zones, and its selector's parameters. Each worldspace is created all at once
in its entirety from a tree of `RegionSpec`s (`world_generation_plan.md`, `## Creating the structure`). `zone_plan.md`
defines worldspaces, regions, and zones, and `world_generation_plan.md` describes how they are generated. The open
items are in `work_plan.md` (`## Zones and regions`).

The design answers one question: **what form do a `RegionSpec` and a `ZoneSpec` take, patterns included, so that a
designer can write one by hand and the game can generate one?** `## Patterns` is the answer so far, and the sections
before it are the keys it builds on. Region specs might later evolve into, or become part of, a general system of specs,
blueprints, or templates for every part of the game.

The top-level region spec defines the worldspace and its top-level region, which spans the entire worldspace, and any subregions and/or zones it contains.
For the initial implementation, subregions will not be supported and the top-level region spec has only zone spec definitions.

Map is a shorthand term for the structure of worldspaces, regions, and zones.

Game spec is not an actual object, but just the set of settings that set up the game so that they can be referenced as a unit.
The game spec includes the starting region spec, the zone position in that worldspace, the position within that zone, and probably quite a few other things.

## The region spec

- **A region spec is a set of settings used to create a region, its subregions, and its zone specs.** It defines the region's properties, and each of
  the region's zones is generated from a `ZoneSpec` derived from it.
- **A region spec may be a definition that many regions are created from,** such as every crypt. It is registered in the
  game's region specs under its own name, which is separate from the names of the regions created from it.
- **Each of a game's top-level region specs creates a worldspace,** with the worldspace's top-level region and the
  subregions the spec defines.
- **Any region spec, and any of its fields, can be generated procedurally from a pattern** as well as written by a
  designer, as can every other part of the world's structure.

## The game's region specs

- **The loaded map has three region spec sources:** predefined, generated by a designer, and generated at random.
- **A game's region specs are in one JSON file in `assets/data/`,** an object of region specs by name. A name is a template's, which many
  regions are created from, or a pregenerated region's.
- **Each top-level region spec in the object defines a worldspace,** such as the surface, a dungeon, or a tower, and a
  region's zones are its direct children. (until subregions are implemented)
- **A game setting specifies the character's initial zone,** a surface zone, and the cell position in it where the
  character starts (`settings_plan.md`). Every other zone is entered through an access point.
- **A form that is easier for designers to work in might come later.**

## Zones of a worldspace

  **A worldspace's extent is defined by its top-level region spec.**
- **A worldspace has a zone at every position of its extent.** Each zone is created empty with the structure, and its
  content is generated the first time it is entered or loaded. A surface worldspace is a grid of zones, and a vertical
  worldspace is a stack.
- **All zones in a worldspace are created empty in worldspace position order**
- **Worldspace position order is `z`, then `y`, then `x`, each from lowest to highest,** with `z` the outermost loop.
- **The order of creation is independent of where the character starts or enters.** A dungeon at `z` -10 to -1 is
  created from -10, and is entered at -1 through an access point.

### Listed zones

A region spec's `zones` list defines individual zones, each by its position and the keys that override the `zone.`
pattern for that zone. Every value can be an expression (`## Patterns`).

| Key | Value |
| --- | --- |
| `position` | The zone's position in worldspace coordinates, within the region's extent |
| `name`, `display_name` | The zone's name and display name, in place of the `zone.` patterns |
| `seed` | The zone's seed, in place of the one drawn from the region's random engine |
| `parameters.*` | Generation parameters, merged over `zone.parameters.*` |
| `generator` | The generator of the zone's content, in place of the selector's choice |
| `zone_template` | The extended name of a pregenerated zone that the zone is built from, in place of a generator |

- **A listed zone with `generator` or `zone_template` is not passed to the selector,** so a designer can place a town
  or a pre-built landmark at a fixed position in a generated region.

## Form

- **A region spec is a structured type,** read from its object in the game's JSON file: values, nested objects such as
  `worldspace` and `zone`, and lists such as `zones`. A member's path is written with `.`, as in `zone.name`.
- **A nested object groups the members for one part of the region,** and a member at the top level is a property of
  the region. The `zone` object is the pattern of an ordinary `ZoneSpec`. Each reader of a spec rejects the members it
  does not read.
- **Each value is a token that its reader parses,** such as `staircase` for an access point type.

## Keys

### Top-level keys

| Key | Value | Read by |
| --- | --- | --- |
| `generator_selector` | The name of the generator selector that chooses how each of the region's zones is generated | `World`, for each zone |
| `seed` | The region's seed, which replaces the one drawn from its parent's random engine | `World` |
| `position.x`, `.y` | The region's position, from which its seed is derived until seeds are drawn hierarchically (`## Seeds`) | `World` |
| region name pattern | The pattern of the names of the regions created from the spec (`## Names`) | `World` |
| metadata | The region's type (surface, dungeon, crypt, ...), terrain, competency level, difficulty, service level, and level count | The selector; some become components on the region |

### `worldspace.`

The `worldspace.` keys of a top-level region spec define its worldspace's coordinate system. The top-level region's
extent defines the worldspace's extent.

| Key | Value |
| --- | --- |
| `worldspace.extent` | One box with every axis given, such as `[{"x": 0, "y": 0, "z": [-10, -1]}]` |
| `worldspace.zone_size.x`, `.y` | The size of each zone in a grid worldspace. Both are given or neither is, and a worldspace with a zone size is a grid |

### `subregion.`

Each `subregion.<name>` key is the entry for a subregion called `<name>`, and the keys under it place and adjust the
subregion.

| Key | Value |
| --- | --- |
| `subregion.<name>` | The name of the registered region spec that the subregion is created from, as in `subregion.barrow_crypt: crypt` |
| `subregion.<name>.extent` | The subregion's extent within the parent's extent |
| `subregion.<name>.count` | The number of subregions created from the entry, 1 if the key is absent |
| `subregion.<name>.spec.*` | Keys that override the registered spec's keys, or the whole spec when the entry has no reference |

- **The parent places each subregion,** since a spec such as `crypt` is reused in parents of different extents.
- **An extent is a list of boxes** in the worldspace's coordinates, and its positions are the union of the boxes. Each
  axis of a box is an inclusive range `[a, b]`, a single integer for one position, or left out, which spans the
  parent's whole range on that axis. Boxes should not overlap, and an overlap is logged as a warning (`world_generation_plan.md`, `### Extents`).
- **A region has a zone at each position of its extent that is in no subregion's extent.**
- **Sibling subregions do not overlap,** and their extents need not fill their parent's extent.
- **A sparse list of `{worldspace_position, region_spec_name}` entries might be one way to specify subregion areas,**
  each entry placing a region spec at a position. It is a preliminary idea that has not been evaluated.

### `zone.`

The `zone.` keys are the pattern of the `ZoneSpec` that each of the region's zones is created from. `World` resolves it
for each zone (`## Patterns`), and the selector completes it.

| Key | Value |
| --- | --- |
| `zone.name` | The pattern of the zone's name, with `{x}`, `{y}`, and `{z}` replaced by its position's coordinates |
| `zone.parameters.*` | Generation parameters for every zone of the region, which the generator reads, such as `zone.parameters.denizens: few` |

`World` sets each zone's `position.x`, `.y`, and `.z` from the region's extent and the worldspace's coordinate system.

### `parameters.`

The `parameters.` keys are the region's generation parameters, which its selector reads. The common selector's
parameters are weighted tables (`world_generation_plan.md`, `### The common selector`):

- **`opening`** is a weighted table for each of the region's first zones, in order.
- **`primary`** is the weighted table for every zone after the opening.
- **`rare`** lists generators or pre-built zones, each drawn with its probability.

A weighted table has one syntax, which placement uses as well (`placement_plan.md`).

## Patterns

- **A pattern is a spec in which a value can be an expression.** Resolving the pattern draws a value for each
  expression and makes a resolved spec, in which every value is a literal. A spec written by hand is a pattern with no
  expressions, so `World` reads both in the same way.
- **A spec is resolved as the structure is created.** A region's spec is resolved when the region is created, and each
  zone's `ZoneSpec` when the zone is created, before the region's generator selector runs for it.
- **A region keeps its resolved spec, and a zone its resolved `ZoneSpec`.** The region and its zones are saved and
  regenerated from them, and a later change to the pattern leaves them unchanged.
- **Resolution draws from a random engine of its own,** seeded from the region's or the zone's seed, which is separate
  from the random engine that draws the seeds of the region's zones and subregions. A change to one expression then
  changes the values drawn from it and no seed.
- **A `seed` key is always a literal,** since resolution is seeded from it.

### Values

| Form | Example | Resolved to |
| --- | --- | --- |
| Literal | `difficulty: 3`, `primary: {fields 4, forest 4}` | The value itself |
| Range | `difficulty: ~3 .. 6` | An integer drawn uniformly from the inclusive range |
| Weighted choice | `subregion.vault: ~{crypt 3, ossuary 1}` | One entry, drawn in proportion to its weight |
| Placeholder | `zone.name: Level {z}` | The value of a variable from the context (`### Context`) |

- **A leading `~` marks an expression,** because a literal can have the same form as one. `primary: {fields 4, forest
  4}` is a weighted table that the common selector draws from for each zone, and `~{fields 4, forest 4}` is one draw
  made when the spec is resolved.
- **A placeholder is replaced in literals and expressions alike.**
- **Arithmetic in an expression would let a value depend on the context,** such as a difficulty that rises with depth:
  `zone.parameters.difficulty: ~{region.difficulty} - {z}`.

### Context

A placeholder refers to a variable of the context that the spec is resolved in.

| Variable | Value |
| --- | --- |
| `{x}`, `{y}`, `{z}` | The zone's position |
| `{index}` | The zone's index in the order in which the region's zones are created |
| `{region.<key>}` | A key of the region's resolved spec, such as `{region.difficulty}` |
| `{parent.<key>}` | A key of the parent region's resolved spec |

### Subregions

- **A subregion entry is a reference with overrides.** `subregion.barrow_crypt: crypt` refers to the registered `crypt`
  spec, and `subregion.barrow_crypt.spec.difficulty: 4` overrides one of its keys. An entry with no reference has its
  whole spec under `.spec.`.
- **A reference that is a weighted choice makes the spec a grammar rule.** `subregion.vault: ~{crypt 3, ossuary 1}`
  expands the region into one of several structures when it is resolved, and a spec that can refer to itself, such as
  a cave that can contain a cave, makes the rule recursive.
- **An entry's `count` can be a range,** such as `subregion.cave.count: ~0 .. 3`. Each subregion created from the
  entry is named by the rules in `## Names`.
- **An entry's `extent` can be an expression that places a box of a given size** at a free position of the parent's
  extent. The positions are drawn as placement draws its sites (`placement_plan.md`, `## A run's roles`), so sibling
  subregions never overlap.

### Zones

- **The `zone.` keys are the pattern of each zone's `ZoneSpec`,** resolved with the zone's position and index in the
  context. The generator selector then completes the resolved `ZoneSpec`.
- **The common selector's tables are a zone pattern.** `opening`, `primary`, and `rare` choose each zone's generator by
  its index and a draw, which an expression on `{index}` could also express.

### Spec generators

- **A spec generator is a registered function that makes a spec,** for a pattern that expressions cannot express, as a
  selector of its own does for zones. It takes the parent's resolved spec, the context, and the resolution random
  engine, and returns a pattern.
- **Spec generators become script** with the selectors (`modding_plan.md`), and until then each is C++ that a host
  registers.

## Names

- **A worldspace and its top-level region have the top-level region spec's name.**
- **A name gets a numeric suffix, as in `<name>_<counter>`, only if the name is taken.** The game has a counter for
  top-level regions, and each region has one for its subregions and its zones, so every extended name is unique.
- **The default name of a zone is `<region name>_{x}_{y}` in a grid worldspace,** and `<region name>_{x}_{y}_{z}` in any
  other worldspace. A vertical region sets its own pattern in `zone.name`, such as `Level {z}`.
- **A zone's display name, shown to players, is separate from its name.** The spec defines how the display name is
  made: from a pattern, from the name reformatted, or at random.
- **A random name that is taken is generated again,** in place of a numeric suffix, and the spec defines how the names
  are generated.

## Seeds

- **Seeds are drawn hierarchically as the structure is created** (`random_engine.md`, `## Generation`). A random engine
  seeded from the world seed draws each top-level region's seed, and each region's random engine draws the seeds of its
  zones and then of its subregions, in the order they are created.
- **A spec's `seed` replaces the drawn seed,** so a region can be regenerated by itself.
- **The order of creation is part of the design,** since it determines every seed.

## Connections between worldspaces

- **An entrance into another worldspace has a zone's extended name as its target,** such as a staircase in a surface
  zone that leads to `barrow/Level -1`. The selector adds the target to the zone's parameters, and the generator writes
  it to the access point.

## The structure World::create builds

For each of the game's top-level region specs, `World::create`:

1. resolves the spec, its subregion entries' counts, references, and extents included, and creates the worldspace from
   the `worldspace.` keys and its top-level region with the spec's name;
2. creates a zone at each position of the region's extent that is in no subregion's extent, in the order of
   `## Zones of a worldspace`, with its position, its seed, its `ZoneSpec` resolved from the `zone.` keys, and its name
   from the pattern, and runs the region's `generator_selector` for the zone;
3. creates each subregion in the same way, from its entry's resolved spec and extent;

and then generates the character's initial zone and places the character at the cell position that the game setting
specifies.

## Other projects

- **Dwarf Fortress** writes its raws as tagged text, with a range as two numbers in a tag, such as
  `[POPULATION_NUMBER:15:30]`.
- **Caves of Qud** has XML population tables of weighted groups, counts in dice notation such as `Number="1d3"`, and
  blueprints that inherit from others with `Inherits`.
- **Cataclysm: Dark Days Ahead** writes its data as JSON, with `copy-from` inheritance, weighted item groups, and
  overmap specials placed on the overmap by their occurrences and allowed locations.
- **Brogue** draws a level's machines from a catalog of blueprints, each with a depth range and a frequency.
- **Grammar-based generators** rewrite a structure by rules: Joris Dormans' mission and space graph grammars, in
  Ludoscope, and CityEngine's CGA shape grammar, in which a rule splits a shape into its parts.

## Open questions

- **Is an expression marked by `~`, or does a schema of each reader's keys define which values are drawn?** A schema
  would also let the game generate a field that no expression is written for, from the key's type and range.
- **Are ranges written as `3 .. 6`, in dice notation, or in both?**
- **Do expressions nest, and do they have arithmetic?**
- **Which variables does the context have?**
- **Do the common selector's tables become `zone.` expressions on `{index}`?**
- **What does a spec generator take and return?**
- **Is a subregion's extent always smaller than its parent's, so that every recursive rule ends?**
- **What are the key names and syntax of an extent and of an expression that places one, and can an extent take forms
  other than boxes?**
- **Are a subregion entry's overrides and a type's patches (`modding_plan.md`) one mechanism?**
- **What are the keys of the region name pattern and the metadata?**
- **Which metadata becomes components on the region, and which does only the selector read?**
- **What properties does each type of region have?** Surface areas and dungeons share some properties and differ in
  others.
- **How does difficulty progress from its starting value across a dungeon's zones?**
- **Does a sparse list of `{worldspace_position, region_spec_name}` entries specify subregion areas, in place of or
  beside `subregion.<name>.extent`?**
- **Which spec defines where an entrance into one worldspace is placed in another?** It might be the surface's, the
  dungeon's, or the game's.
- **Is `GeneratorSelection::region_spec_name`, a selection that creates a new region, still needed once every region is
  created before play starts?**
- **How is a display name made, and how are random names generated?**

## Contents of a region spec

A region spec has the members below. Built members are read by the code now, designed members are in `world_generation_plan.md`
or `zone_plan.md`, and proposed members are in this plan alone.

| Member | Contents | State | First implementation |
| --- | --- | --- | --- |
| `generator_selector` | The name of the generator selector that chooses how each zone is generated | Built | Yes |
| `seed` | The region's seed, in place of the drawn one | Built | Yes |
| `position.x`, `.y` | The region's position, which its seed is derived from until seeds are drawn hierarchically | Built | No |
| `worldspace.extent` | A top-level spec's worldspace extent, one box; built as interval strings on each axis | Built | Yes |
| `worldspace.zone_size.x`, `.y` | A grid worldspace's zone size | Built | Yes |
| `zone.name` | The pattern of each zone's name | Built | Yes |
| `zone.display_name` | The pattern or rule for each zone's display name | Proposed | Yes |
| `zone.parameters.*` | Generation parameters for every zone | Designed | Yes |
| `parameters.opening`, `.primary`, `.rare` | The common selector's weighted tables | Designed | Yes |
| metadata | Type, terrain, competency level, difficulty, service level, and level count; key names open | Designed | Yes |
| region name pattern | The pattern of the names of regions created from the spec; key name open | Designed | No |
| `zones` | Listed zones, each a position with overrides of the `zone` pattern, a generator, or a pregenerated zone | Proposed | Yes |
| `subregion.<name>` | The registered spec a subregion is created from | Designed | No |
| `subregion.<name>.extent`, `.count`, `.spec.*` | The subregion's placement, its count, and overrides of its spec | Proposed | No |
| Any value | A literal, or an expression drawn when the spec is resolved (`## Patterns`) | Proposed | No |
